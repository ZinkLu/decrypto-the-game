# 画质与性能

画质是页面右上角“设置”里的一项：自动 / 高 / 中 / 低。它属于这次会话的页面设置，不是机器上的零件。本文说明每一档关掉什么、自动档怎样选、机器闲着时怎样省电。代码在 `web/src/console/quality.ts`、`engine.ts`（`applyQuality`、帧循环的节奏）、`partialFrame.ts` 和 `partialRedraw.ts`（氛围帧的局部重画）。

## 档位

每一档是 `qualityProfiles` 里的一行。引擎应用的、设置里悬停提示显示的，都是这同一张表，所以提示不会和实际行为不一致。切换立即生效，不重新载入。

| 开关 | 高 | 中 | 低 | 含义 |
| --- | --- | --- | --- | --- |
| `pixelRatio` | 2 | 1.5 | 1 | 设备像素比的上限 |
| `areaLights` | 开 | 关 | 关 | 两盏大面积的影棚灯（`RectAreaLight`） |
| `shadows` | 开 | 开 | 关 | 主光的阴影（PCF，1024 贴图） |
| `screenGlass` | 开 | 开 | 关 | 六块显像管前的物理玻璃 |
| `nixieCover` | 开 | 开 | 关 | 辉光管的亚克力罩和管壳玻璃 |
| `crtOptics` | `full` | `full` | `lite` | 显像管的光学效果 |
| `ambientFps` | 60 | 30 | 30 | 有人操作时氛围动画的帧率 |
| `backdropBlur` | 开 | 开 | 关 | 纸带阅读器背后的 CSS 模糊 |

高档是完整的机器，往下每一档只减不增。

几点说明：

- **关掉面光源后**，主光、补光和天光的强度乘以 1.26，整体曝光不变。看得出的差别是投影的边缘略硬。
- **`lite` 光学**把画面直接印在面板上：不计算穿过玻璃的折射，没有光晕采样，没有色散。扫描线、滚动带、闪烁和颗粒保留。显像管上的输入框要跟着画面走，所以 `engine.bounds()` 把同一个选择传给 `crtDisplayUv`，两种光学下输入框都对得上字。
- **画质不改变交互动画。** 任何一档都不缩短、不省略玩家触发的动作。它和系统的“减少动态效果”设置互不相关。

每一档都保留的：

- **环境反射。** 去掉它，金属就失去质感；其他低档开关都关掉之后，再去掉它也省不了多少。
- **MSAA。** 抗锯齿在创建 WebGL 上下文时确定，之后无法切换。

窄屏布局用紧凑终端代替 3D 舞台，那里不显示画质选择。舞台没有尺寸时引擎不渲染。WebGL 启动失败时也不显示。

## 自动档

自动档实际测量，不看硬件型号。

1. 模型载入后，引擎先渲染 8 帧，让着色器编译完成、管线稳定。
2. 接着连续渲染四分之一秒，帧与帧之间不等显示器刷新。每帧渲染后读回一个像素，迫使 GPU 把这一帧做完，测到的时间才包含 GPU 的部分。
3. 取后一半样本的中位数作为单帧耗时。只看后一半是因为空闲的 GPU 会降频，刚开始的几帧偏慢。
4. 单帧不超过 13 ms（`frameBudget`）就留在当前档位。13 ms 给合成器和页面的其余工作留出了 16.7 ms 里剩下的部分。
5. 超过时降档：高档测得不超过 36.4 ms（13 × 2.8）降到中，否则直接降到低；中档超过就降到低。2.8 是实测的高、中两档 GPU 耗时之比。降档后再测一次，直到合格或到达低档。

自动档只会往下走，不会因为某一帧快就往上试。结果存在 `decrypto-quality-auto`，下次访问从这一档开始，不必每次都从高档重来。再点一次“自动”会从高档重新测量。

## 氛围帧与闲置

引擎把帧分成两类：

- **有变化的帧**：玩家改了什么，或者零件、显像管、纸带还在动。这类帧立即渲染，每次显示刷新一帧。
- **氛围帧**：只有扫描线、示波器光点和仪表指针在动。这类帧按节奏渲染。

氛围帧的帧率由 `ambientRate()` 决定：

| 情况 | 帧率上限 |
| --- | --- |
| 有人在操作 | 该档位的 `ambientFps` |
| 10 秒没有指针、键盘或滚轮输入 | 30 |
| 窗口失去焦点 | 20 |

上限和档位自己的帧率取较小者。20 帧是示波器模拟的步长，再低光点就不连贯。下一次输入立即恢复档位的帧率。

少画的帧不会丢信息：示波器在下一次渲染时补算自上次显示以来的全部时间，被跳过的指针动作记为欠账，下一帧画出它的当前位置。

机器断电或系统要求减少动态效果时，没有氛围帧。翻到背面时背面没有氛围动画，只到节奏才该画的帧直接跳过。

### 氛围帧只重画在动的区域

相邻两个氛围帧之间只有约 0.3% 的像素在动：显像管的扫描线和光标、示波器光点、辉光管呼吸、LOCK 灯、接收机指针。整幅重算这帧是浪费，所以氛围帧分两步画：先把上一整帧的副本原样铺回，再只在会动的几块区域里重新渲染。有真实变化的帧（旋钮、纸带、翻面、状态更新）照旧整帧重画，时机和代价都不变。

- **副本**：一整帧画完后立刻拷到一张和画布一样大的贴图（`copyFramebufferToTexture`）。只有画面即将停住的整帧才拷——带着变化或正在测速的整帧不拷，连续交互因此没有任何额外开销；动作停下后的第一帧本来就是整帧，顺带拷一次。拷贝必须在同一个任务里完成：画布不保留绘制缓冲，出了这个任务就读不到了。另外每个页面的第一个局部帧画完后会立刻和同一状态的整帧逐像素自检一次，拷贝失败或自检不一致（有的浏览器两帧渲染就不是逐位稳定的）时，本页永久退回整帧，开发服务器的控制台会说明原因。
- **副本作废**：窗口尺寸或画质变化、自动档测速、`partialRedraw` 从关到开，副本都作废；下一帧回到整帧并重拷。
- **动态区域**：每个会自己动的部件通过 `ambientRegions()` 登记自己在动的物体——显像管平面（含玻璃，LED 词窗只在跑马灯爬行时登记）、辉光管的光晕和余辉、LOCK 灯的网格、接收机的整块表盘玻璃。拷贝时把它们的包围盒投影成画布上的矩形，外扩 6 px、裁到画布内、相交合并。矩形外是副本的像素，矩形内和整帧一样完整渲染，所以两种帧逐像素相同。
- **画法**：通道开始时把深度清成 0，铺回副本，再在每个矩形里把深度清回 1，然后整个场景只渲染一遍。矩形外的片元过不了深度测试，不会被着色；几何只处理一次。
- **以后新增任何氛围效果，都必须登记区域**，否则它在局部帧里会冻住。`?partial=verify` 能抓出漏登记的区域（见"开发时查看"）。

实现时要注意的几点：

- **纯色背景会强制清屏。** `scene.background` 是颜色时，three 每次 `render()` 前都清掉颜色、深度和模板，不看 `autoClear`。局部帧里要把 `autoClearColor`、`autoClearDepth`、`autoClearStencil` 都关掉，否则副本和深度遮罩被抹掉，这一帧实际上又成了整帧。
- **副本原样铺回。** 它存的是色调映射、sRGB 编码之后的字节，要用不含颜色空间代码的 `ShaderMaterial` 铺回；`MeshBasicMaterial` 会再转换一次。
- **不用 `preserveDrawingBuffer`。** 它和 4× MSAA 一起用时，每个整帧都要把多重采样数据写回内存，5K 下整帧功耗涨三到五成。
- **不要每个矩形各渲染一遍场景。** 那样每个矩形都要把整机的几何重新处理一遍，9 个矩形在 60 帧时仍要约 +8 W；深度遮罩只处理一遍。
- **会动的物体的区域要盖住它扫过的整个范围。** 接收机指针登记的是整块表盘玻璃：只用指针自己的包围盒，离开的位置会留下残影。
- **在氛围帧里被改动的材质，用到它的网格都要登记，且不能被合批。** LOCK 灯的材质由 `Lamps` 用 `chassis.claim()` 留在批次之外。
- **阻尼动作要能落停。** 报告 `Effect` 的门限之下如果还在缓慢漂移，漂移的像素没有帧会重画，副本就在那里失准。旋钮、指针和说明键因此用 `settle()` 或到阈值直接取目标值。

### 循环会睡眠

一次 `tick` 如果什么都没画、也没有东西在动，就不再请求下一次显示刷新。它设一个定时器，在下一个氛围帧、指示灯超时或最多 500 ms 之后醒来。任何输入事件和引擎的每个公开方法都会立刻唤醒循环。页面隐藏时不渲染。

## 实测

以下数字是在一台 Apple M4 Max 上测的，场景是对局后期的整机（`?preview=late-game`）。它们说明各项开销的相对大小，换一台机器数值会不同。

### 每个开关单独关掉能省多少

在 2880×1800 下逐个关闭，对照每帧 5.9 ms 的同步渲染。斜杠前是 GPU 上省下的比例，斜杠后是软件光栅化（1440×900）下的比例。

| 开关 | 节省（GPU / 软件光栅化） |
| --- | --- |
| `pixelRatio` 降到 1.5 | 34% |
| `pixelRatio` 降到 1 | 51% |
| `areaLights` | 46% / 28% |
| `shadows` | 20% / 13%，另加每次阴影贴图刷新（189 次绘制调用，49.2 万三角形） |
| `screenGlass` | 22% / 10% |
| `nixieCover` | 15% / 8% |
| `crtOptics` 改为 `lite` | 最多 15% / 12% |
| `ambientFps` 减半 | 稳态负载减半 |
| `backdropBlur` | 未测 |

各项互相重叠，不能相加。整档的单帧耗时：高 5.2 ms，中 2.6 ms，低 1.8 ms。整机约 64.5 万个三角形，几何量不是瓶颈。

### 闲置的开销

2026-09-30 测量，窗口在 5K 显示器上（画布 5120×2600，高档，`?preview=late-game`），功耗由 `power.mjs` 测得并已扣除同一轮的基线；局部帧的开关在同一轮里交替，5 轮取中位数。

看功耗，不看“GPU 占用”：M4 Max 的 GPU 有 15 档频率（338–1578 MHz），macOS 按负载调频——活少降频、活多升频。所以各种配置在活动监视器里的占用都差不多（30 帧时都在 15–30%），功耗却能差十几倍：频率越高电压越高，同样的活耗电多得多。这里的数字都是瓦数。

| 状态 | 帧率 | 局部帧关 | 局部帧开 |
| --- | --- | --- | --- |
| 停手超过 10 秒 | 30 | +9.3 W | +1.8 W |
| 鼠标在页面上移动 | 60 | +16.5 W | +4.0 W |
| 拧旋钮 | 60 | +18.1 W | +3.9 W |
| 窗口在后台 | 20 | +5.2 W | +1.1 W |

GPU 的平均频率随之从 1.3–1.5 GHz 降到 650–750 MHz。拧旋钮时也省：每次拨动之后旋钮很快停住，停住后的帧就是局部帧。

内建屏（画布 3024×1800，2026-09-29 测量）约为三分之一：停手 +2.6 → +0.7 W，动鼠标 +4.5 → +1.6 W，后台 +1.8 → +0.6 W。

局部帧只改变氛围帧的画法：交互帧仍是整帧，帧率不变（30/60/20）。60 帧的两种状态里 GPU 会在高低频之间跳动（低频时帧率掉到 40 多、功耗约一半），单轮读数差可达 ±20%，所以必须在同一轮里交替开关、取中位数。高档一帧的 GPU 时间约 7–9 ms，其中逐像素光照占约八成（两盏面光源占四到五成，4× MSAA 约四成），几何只占约 5%——所以把 99.7% 不动的像素换成一次贴图回铺，省下的正是光照。

### 测过但没有采用的做法

下面几项都能再省电，但都会改变高档的外观，所以没有采用。数字是 5K、高档、30 帧、局部帧关闭时的 GPU 功耗，同样的测法。

| 做法 | GPU 功耗 | 外观变化 |
| --- | --- | --- |
| 现状 | +8.6 W | — |
| 关掉两盏面光源（其余灯光乘 1.26，即中档的做法） | +3.0 W | 辉光管玻璃和面板上柔和的反光没了 |
| 关掉 4× MSAA | +5.7 W | 指针、刻度这类细斜线有轻微锯齿；换成 FXAA 会把小字弄糊 |
| 像素比从 2 降到 1.5 | +3.8 W | 主屏文字略软 |
| 像素比 1.5 再关 MSAA | +2.1 W | 上面两项叠加 |
| 高档氛围帧从 60 降到 30 | 只影响动鼠标时：约 +15 → +8.6 W | 扫描线、示波器、指针每秒刷新 30 次 |

按总像素封顶只有上限设在约 750 万像素时才起作用：5K 全窗口是 1330 万像素。把光照烘焙进贴图能让交互帧也变便宜，但灯光就不能再改，会动的零件和随视角变化的高光仍要实时计算，模型也会变大。

## 重画的开销

`paint()` 每次都画出全部表面，开销主要在主线程。有四处专门处理：

- **倒计时钟单独画。** 倒计时每秒变一次，其他表面不变。`paintClock()` 只画这一张 520×218 的贴图。见[代码组织](code.md)里关于 `paintKey` 的说明。
- **主屏按 canvas 身份更新。** `paint()` 返回新的主屏 canvas 就上传，同一张 canvas 不重复上传。主屏的单个数字、横杠等小字形变化不能依赖缩略图判断，选满最后一位、替换和删除都要立即显示。旋钮等模拟输入仍由 `paintKey` 排除，不会因此重画主屏。
- **其他表面用近似哈希去重。** `paint()` 总是返回新的 canvas；除主屏外，引擎比较缩略图哈希，相同就不上传。最长的纸带贴图上传最贵，它大多数时候不变。
- **哈希一次读回。** 从 canvas 读像素要等 GPU，逐张读很慢。引擎把需要哈希的 canvas 缩成 32×32，拼进一张图集，只读回一次。这是有损采样，可能漏掉细小像素差异，所以主屏不参与。61 个表面逐张读要 26 ms，合在一起读要 6 ms。

合起来，倒计时走一秒占用的主线程时间从 31 ms（最高 48 ms）降到 8 ms。

阴影贴图不自动更新（`shadowMap.autoUpdate = false`），只在零件移动的那些帧刷新。不停摆动的指针和旋钮指示线太小，在阴影贴图里看不出来，所以不投影，静止的阴影就不必跟着重算。

## 开发时查看

开发服务器上，渲染画布的 `data-` 属性每 750 ms 更新一次：

| 属性 | 内容 |
| --- | --- |
| `data-scope-fps` | 实际渲染的帧率 |
| `data-draw-calls` | 绘制调用数 |
| `data-triangles` | 三角形数 |
| `data-ambient-pace` | 当前氛围帧率上限 |
| `data-face` | `front` 或 `rear` |
| `data-full-frames` | 整帧累计数 |
| `data-partial-frames` | 局部帧累计数 |
| `data-partial-mismatch` | `?partial=verify` 下局部帧与整帧不同的像素累计数（仅校验模式） |

加上 `?quality=high|medium|low|auto` 可以为一次截图或测量固定档位，不改动保存的选择。见[开发预览](preview.md)。

局部帧有两个开发参数。`?partial=off` 整页只画整帧，用来对比。`?partial=verify` 每画一个局部帧就把它和同一状态的整帧逐像素比较，不一致会在控制台警告并把像素数累加到 `data-partial-mismatch`；校验要逐帧读回两遍整幅画面，很慢，只用来检查。

引擎实例在开发服务器上是 `window.__consoleEngine`。`web/scripts/perf/` 下的探针都通过它读写引擎，在无头 Chrome（真实 GPU）里测功耗、帧耗时和变化的像素：

```bash
cd web && pnpm dev                          # :3000
cd web/scripts/perf && ./chrome.sh          # 无头 Chrome，CDP 端口 9555
caffeinate -dimsu node power.mjs --size 2560x1300@2 --rounds 5
```

`power.mjs` 在引擎自己的节奏下测停手、动鼠标、拧旋钮、后台四种状态的帧率和 GPU 功耗，并在同一轮里交替开关 `partialRedraw` 做对比；`frame-cost.mjs` 背靠背满频渲染，拆出每个开关占一帧的比例；`dirty-map.mjs` 标出氛围帧里哪些像素在变；`partial-prototype.mjs` 是局部帧的原型。显示器睡过之后 Chrome 可能失效（日志里有 `CVDisplayLinkCreateWithCGDisplay failed`），重跑 `./chrome.sh` 即可。
